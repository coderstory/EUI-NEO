# 平台能力

页面代码通过 `eui/platform.h` 使用平台能力；底层实现位于 `core/platform/platform.h` / `core/platform/platform.cpp`。这里放跨平台、非业务的系统集成能力，例如打开 URL、文件选择对话框、托盘、IME 光标位置同步。

`core/` 中的 API 命名必须保持通用。文件选择只表达“选择文件”，不要在核心层写成媒体、图片、配置文件等业务概念；具体业务类型由调用方传入选项。

## 打开 URL

```cpp
eui::platform::openUrl("https://github.com/sudoevolve/EUI-NEO");
```

平台实现：

- Windows：`ShellExecuteA`
- macOS：`open`
- Linux：`xdg-open`

返回 `true` 表示系统接受了打开请求，不代表目标 URL 一定加载成功。

## 文件选择

推荐使用 `openFileDialog(...)`，它能区分选中、取消和失败：

```cpp
const eui::platform::FileDialogResult result =
    eui::platform::openFileDialog({
        "Select image",
        {".png", ".jpg", ".jpeg", ".webp"},
        "assets",
        "Images"
    });

if (result.selected()) {
    const std::string path = result.paths.front();
}
```

当前公开 API：

```cpp
struct FileDialogOptions {
    std::string prompt;
    std::vector<std::string> allowedExtensions;
    std::string initialDirectory;
    std::string filterName;
    bool allowMultiple = false;
};

enum class FileDialogStatus {
    Selected,
    Cancelled,
    Failed
};

struct FileDialogResult {
    FileDialogStatus status = FileDialogStatus::Cancelled;
    std::vector<std::string> paths;
    std::string error;

    bool selected() const;
};

eui::platform::FileDialogResult openFileDialog(const FileDialogOptions& options = {});
std::string chooseFile(const FileDialogOptions& options = {});
std::vector<std::string> chooseFiles(const FileDialogOptions& options = {});
```

### 选项说明

- `prompt`：对话框标题或提示文本。为空时使用默认提示。
- `allowedExtensions`：允许选择的扩展名列表。可以写 `"png"`、`".png"` 或 `"*.png"`；内部会统一转换。为空表示不过滤。
- `initialDirectory`：初始目录。为空时由系统决定默认位置。
- `filterName`：过滤器显示名称，例如 `"Images"`、`"Text files"`。为空时使用通用名称。
- `allowMultiple`：是否允许多选。`chooseFiles(...)` 会自动打开多选；`chooseFile(...)` 会强制单选。

### 类型过滤

类型过滤是扩展名过滤，不做文件内容探测。例如：

```cpp
eui::platform::FileDialogOptions options;
options.prompt = "Select data file";
options.allowedExtensions = {".json", ".csv", ".txt"};
options.filterName = "Data files";
```

平台转换方式：

- Windows：原生 `GetOpenFileNameW` 过滤器，例如 `*.json;*.csv;*.txt`。
- macOS：AppleScript `choose file of type {"json", "csv", "txt"}`。
- Linux：`zenity --file-filter`，不可用时回退到 `kdialog` 过滤器。

### 简单入口

不需要区分取消和失败时，可以使用兼容型入口：

```cpp
const std::string path = eui::platform::chooseFile({
    "Select file",
    {".txt", ".md"}
});

if (!path.empty()) {
    // user selected a file
}
```

多选：

```cpp
const std::vector<std::string> paths = eui::platform::chooseFiles({
    "Select files",
    {".png", ".jpg"}
});
```

`chooseFile(...)` 和 `chooseFiles(...)` 在用户取消或平台失败时都会返回空结果。需要展示错误信息时，使用 `openFileDialog(...)` 并检查 `result.status` / `result.error`。

### 结果处理

```cpp
const auto result = eui::platform::openFileDialog({
    "Select file",
    {".json"}
});

if (result.status == eui::platform::FileDialogStatus::Selected) {
    // result.paths
} else if (result.status == eui::platform::FileDialogStatus::Cancelled) {
    // user cancelled; usually no UI error needed
} else {
    // result.error contains a diagnostic message
}
```

## 平台依赖

- Windows：使用系统 Common Dialog，不需要额外运行时工具。
- macOS：使用系统 `osascript` 调用 `choose file`。
- Linux：优先使用 `zenity`，失败时尝试 `kdialog`。两者都不可用时，`openFileDialog(...)` 返回 `FileDialogStatus::Failed`。

## 当前限制

- 目前只支持打开本地文件。
- 暂不支持选择目录、保存文件、默认文件名、父窗口/modal 绑定。
- 文件选择是阻塞式系统对话框。适合在按钮点击回调里调用；不要在每帧 compose/update 中调用。

## 窗口效果（`core/platform/window_effect.h`）

标题栏外观（`applyTitleBarAppearance`）与 DWM backdrop（`applyWindowEffect`）的平台支持矩阵（磨砂设计文档 §3.6 降级链）：

| 能力 | Windows | macOS | Linux |
|---|---|---|---|
| 标题栏深浅联动（`TitleBarAppearance.dark`） | ✅ Win11 22000+（`DWMWA_USE_IMMERSIVE_DARK_MODE`） | ✅ `[NSWindow setAppearance: Aqua/DarkAqua]`（跟随宿主主题，不是系统外观） | ❌ |
| 自定义标题栏底色（`customColor` / `colorAlpha`） | ✅ Win11 22000+（`DWMWA_CAPTION_COLOR`；无 alpha 概念，`colorAlpha` 被忽略） | ✅ 窗口背景 = 该色（含 `colorAlpha`）+ `titlebarAppearsTransparent=YES` → 标题栏 = 宿主主题底色、与内容区同透明度 | ❌ |
| 透明帧缓冲半透（`WindowEffect::Transparent`） | ✅ GLFW 后端（需桌面合成；SDL2/Vulkan 降级 None） | ✅ GLFW 后端（`GLFW_TRANSPARENT_FRAMEBUFFER`；**注意 macOS 该属性由 `![NSWindow isOpaque]` 推导**，实现内不得改 `isOpaque`——GL 后端把该属性缓存在首个渲染帧选 blit 路径，改了会带偏会话级真值） | ❌ |
| Acrylic/Mica/MicaAlt backdrop | ✅ Win11 22H2（22621）+ GLFW 后端（`DWMWA_SYSTEMBACKDROP_TYPE`；能力缓存，失败静默降级） | ✅ `NSVisualEffectView`（`window_effect_macos.mm`；材质视图垫在 GL 视图之下，物性取值待实机复核） | ❌ |
| 非客户区（标题栏条）底色 | ✅ 系统代画（DWM backdrop 贯通非客户区） | ✅ 两条互斥取值（见下方机制说明）：宿主给了 `customColor` → 窗口背景 = 该色（**标题栏 = 内容区底色**）；没给 → 「全透明非 clear」色，由 AppKit 画自画标题栏底（深浅随窗口 `NSAppearance`） | ❌ |

不支持的平台/版本：`applyWindowEffect`/`applyTitleBarAppearance` 返回 `false`，调用方（`glfw_app_main`）按透明帧缓冲实际状态降级为 `Transparent`/`None` 并回写 `app::activeWindowEffect()`。运行时 API 与配置入口见 `docs/DSL.md`「窗口效果」一节。

### macOS 标题栏底机制（2026-09-29 真机取证定案）

1. **AppKit 对「背景 == `[NSColor clearColor]` 的非不透明窗」不画标题栏底** ⇒ 整条标题栏（含交通灯那行）透出下层窗口/桌面；黑壁纸下与「全透明」无法区分（用户原始投诉即此）。
   修法：平台层把窗口背景替换为**全透明但非 clearColor** 的具体颜色（alpha=0，不引入着色）→ AppKit 恢复画标题栏底。
   真机对照（同构建·磨砂档）：替换前标题栏行 = 下层窗口颜色（浅色窗 250,249,245 / 深色窗 59,58,56，随背景变）；替换后 = (255,255,255) 恒定；对照组用半透明红@0.5 会把内容区染成 (242,217,210) → 必须 alpha=0（alpha=0 组内容区像素与不替换时逐项相同）。
2. **标题栏材质深浅只跟窗口外观（默认=系统外观），不跟宿主主题** ⇒ 应用浅色 + 系统深色时标题栏发暗，同样像「全透明」（用户环境的夜间情形）。
   修法：`applyTitleBarAppearance`（Windows 语义 = `DWMWA_USE_IMMERSIVE_DARK_MODE`）在 macOS 落到 `[nsWindow setAppearance: Aqua/DarkAqua]`。
   真机对照：深色主题 + 浅色系统 → 修前标题栏 (250,249,245)（= 下层浅色窗，错），修后 (36,36,36)；浅色主题 → (255,255,255)。
3. **`customColor` 在 macOS 有对应物：窗口背景色就是标题栏的底**（宿主 DevDesk 需求：标题栏要跟随主题、「和 content 融为一体」）。`applyTitleBarAppearance` 收到 `customColor` 时执行
   `setBackgroundColor(该色, colorAlpha)` + `setTitlebarAppearsTransparent(YES)` ⇒ AppKit 不画自画材质，标题栏区域直接透出窗口背景色 = 内容区底色（同色、同透明度）。
   三档窗口效果因此都成立：实色 colorAlpha=1.0 / 半透 0.90 / 磨砂 0.65（**2026-09-29 二版起 DevDesk 显式传 `customColor`**，标题栏那层 alpha 与 `clearColor` 的 alpha 解耦，见下方「已知限制」第二条；本句描述的「按 `clearColor` 同色同透明度推导」仍是没显式传 `customColor` 时的兜底行为）。
   宿主只调 `app::setClearColor` 也能生效：调用方 `glfw_app_main.cpp::applyTitleBarAppearanceToWindow` 在 **macOS** 上用当前 `clearColor`（= 内容区底色，含窗口效果档 alpha）兜底填 `customColor`，并在 clearColor 变更（主题切换 / 窗口效果切档）时额外重刷一次标题栏（标题栏外观检测看不出「只改 alpha」的变更）。Windows 侧不做这个推导：`DWMWA_CAPTION_COLOR` 与窗口背景色不是一回事（推导会让标题栏与内容不同色），Windows 行为逐字不变。

三条都不动窗口结构（不碰 contentView / GL 视图 / FullSizeContentView），几何零风险；实测三档 `windowSize=(1470,801) framebuffer=(2940,1602) contentScale=(2.000,2.000) dpiScale=2.0000 uiScale=1.0000 logical=(1470.00,801.00)` 与 `styleMask=0xf frame=(0,90,1470,833)` 均不变；第 3 条改前/改后 `[fxdiag]` 的 `contentRect / layoutRect / contentView frame / hosted(GL 视图) frame / material frame / styleMask / isOpaque` 逐项相同，只有 `bg` 与 `tbTransparent` 两位变化。

#### 真机像素取证（窗口级截图 `screencapture -x -o -l <windowID>`，**含 alpha 通道**，与桌面背景无关；浅色主题 `#FAF9F5` = 250,249,245）

| 窗口效果档（clearColor alpha） | 改前 标题栏 | 改前 内容区 | 改后 标题栏 | 改后 内容区 |
|---|---|---|---|---|
| 关闭（1.0） | (255,255,255,255) | (250,249,245,255) | **(250,249,245,255)** | (250,249,245,255) |
| 半透（0.90） | (255,255,255,255) | (251,249,245,229) | **(251,249,246,229)** | (251,250,246,252) |
| 磨砂（0.55） | (255,255,255,255) | (242,242,240,255) | **(250,250,246,140)** | (242,242,240,255) |

改前标题栏三档恒为不透明纯白（AppKit 自画材质 = 用户投诉）；改后三档都取宿主主题底色与档位 alpha，实色档与内容区逐项相同。

### 已知限制（macOS）

- **标题栏与内容区的透明度残差（2026-09-29 二版已解到目标内）**：窗口背景同时位于 GL 内容**之后**，故内容区层数比标题栏多一层（clearColor 纱 / 材质）。二版前两处 alpha 由同一 `clearColor` 推导成同一值，磨砂档（0.30）黑壁纸实测标题栏 (75,75,74) vs 内容区 (180,181,179) = **差 105/255**。二版两处改动同时落地：① 材质贯通标题栏（下一条）；② DevDesk 显式传 `customColor` 把两处 alpha 解耦（半透 0.45/0.90、磨砂 0.15/0.65）→ 黑壁纸实测 半透 标题栏 225 / 内容区 236.5（差 11.5）、磨砂 标题栏 192 / 内容区 200.7（差 **8.7**）、关闭档三区恒 (250,249,245)。
- **材质「贯通」标题栏（2026-09-29 二版实作）**：material 档在标题栏那一条（窗口矩形 − 客户端矩形，实测 `(0,801,1470,32)`）另挂一份与内容区**同材质/同混合/同 state** 的 `NSVisualEffectView`，两份都不是 GL 视图的再挂载 → 几何零位移；材质视图是 `NSThemeFrame` 的底层子视图，按钮/标题压在它上面，且 `hitTest` 恒 nil（事件透明）→ 标题栏拖拽真机复验可用（拖动后窗口下缘 1731→1831 物理像素）、红绿灯悬停 glyph 正常。
  两次失败尝试（真机取证，勿重走）：① `NSWindowStyleMaskFullSizeContentView` + contentView 容器 + 主题色条底 —— 实测 **FSCV 把 GL surface 整体下移一个标题栏高（32pt）**：内容位移（亮段 114/219pt → 143/244pt）、底部被裁、标题栏与内容间留 66..95pt 全透明空带；② 单张材质视图铺满整窗挂在 `NSThemeFrame` 上（不碰 FSCV、不碰 GL 视图）—— 实测 **AppKit 把窗口标题画到最左缘、与红绿灯重叠**（全窗/条状两种 frame × `relativeTo:nil`/`contentView` 两种插入点 × 含/不含 hitTest 覆写，四组合全复现）。最终采用「内容区那份一字不动 + 额外一条只盖标题栏的子视图挂在**内容区材质之下**（子视图顶出内容矩形，由窗口绘制边界裁剪）」。
  事件注意事项：内容区材质**必须**保持默认 `hitTest`（它是 contentView、GL 视图的父视图，覆写成 nil 会让整棵内容区子树收不到鼠标事件——实测侧边栏点击全失效）；只有标题栏条那份用 `EUIPassthroughMaterialView`。
- **macOS 上不得在运行期改窗口不透明性**：`GLFW_TRANSPARENT_FRAMEBUFFER` = `![NSWindow isOpaque]`
  （`3rd/glfw/src/cocoa_window.m` `_glfwFramebufferTransparentCocoa`），GL 后端把该属性缓存在首帧用于选择
  straight/premultiply blit 路径（`core/render/opengl/opengl_backend.cpp` `outputUsesTransparentFramebuffer`）→
  运行期 `setOpaque:` 会让会话内的 blit 路径与实际窗口状态不一致（切档后 alpha 合成出错）。
- **曾短暂存在的两个连带问题（已修）**：① 按档位 `setOpaque:YES` 带偏上述缓存；② 「None 档成功回写」让宿主半透档
  降级提示恒误报（`applyWindowEffectToWindow` 现按「透明帧缓冲是否生效」统一折法，macOS 分支）。
- Windows 侧「`WindowEffect::None` 成功回写 vs 半透档降级判据」的同一不一致已知（详见
  `core/app/glfw_app_main.cpp` `applyWindowEffectToWindow` 内 `#else` 注释），待有 Windows 实机时另行处理。
